# Project audit — October 29, 2026

**Overall rating: 4/10 for the current state as a production portfolio.** The project has a coherent identity, an understandable architecture, and working happy paths. However, public filesystem traversal, reproducible data loss, full-page frontend crashes, and weak operational safeguards prevent a higher production-readiness score. The design direction and basic architecture are stronger than this score; the score reflects what happens when real inputs, navigation, failures, and concurrent requests reach the implementation.

I reviewed the current working tree, including existing staged and unstaged changes, both DEVDOC files, all application source, configuration, dependency manifests/locks, and the local content structure. Existing application code and content were left unchanged. This report is the only new repository file.

The intended product is an Xcode-inspired developer portfolio, a Markdown blog, and public app privacy/support pages. Its backend deliberately uses JSON files and image files so it can run on cPanel/Passenger without a database, CMS service, or background workers. That is a reasonable scope for a personal site. The central problem is that the implementation treats filesystem persistence, incoming JSON, and asynchronous UI state as safer and simpler than they actually are.

**Validation performed.** Both production builds pass. Frontend lint fails with **9 errors and 4 warnings**. A supplementary frontend TypeScript check with `--strict` also passes, despite strict mode not being enabled in its app configuration. I ran isolated HTTP tests against a compiled backend copy, using temporary content and a temporary token; I ran the built frontend in headless Chrome against controlled API fixtures at desktop and mobile sizes. I checked the current npm advisory registry and relevant upstream security advisories. I did not test or modify the live deployment, inspect hosting controls, or attempt to read real secrets through the vulnerability. Browser fixture tests establish application behavior, not live-site performance or uptime.

| Area | Assessment |

These are qualitative assessments, not an arithmetic scoring formula. Security and data integrity are release gates.

**What is already working well.** Routes, components, and storage helpers are easy to locate. The backend has little unnecessary machinery. Precomputed list/navigation projections avoid rescanning every content file on each public list request. Markdown uses the standard renderer without enabling raw HTML. External links generally include `noopener noreferrer`. Write routes consistently require authentication, and uploads authenticate before invoking Multer. Uploads have a compressed-file size limit and strip metadata through WebP conversion. Heavy pages are split into separate bundles. The local records and generated indexes currently agree, and the 320px home layout did not overflow in the browser check. These are useful foundations worth preserving.

The findings below distinguish **reproduced** failures from **source-confirmed** defects and **operational risks** that were not exercised against production. High means fix before relying on the site in production; medium means a meaningful correctness, usability, or maintenance problem; low means polish or a limited edge case.

1. **High — Public API requests can read JSON outside the content directory. Reproduced.** [projects.ts:45](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/projects.ts:45), [posts.ts:50](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/posts.ts:50), [apps.ts:24](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/apps.ts:24).

   IDs are interpolated into paths without validation or containment checks. Express decodes encoded slashes inside a route parameter; `join()` then resolves `..` segments. In a disposable backend, `GET /api/projects/..%2F..%2Faudit-sentinel` returned HTTP 200 with a sentinel JSON file stored outside `data/projects`. No authentication was needed. The post detail route has the same construction. App routes also accept uncontained directory paths, although their target filenames are fixed.

   This exposes accessible JSON files at predictable paths, potentially including private configuration on the same hosting account. It is not unrestricted arbitrary-file reading: these routes append `.json` or a fixed JSON filename, and JSON parsing must succeed. The test did not access actual secrets. Enforce a single slug grammar at every boundary, reject separators/dot segments and reserved names, and verify resolved paths remain under their intended root. Account for symlinks if the deployment can contain them. Test encoded traversal, not just literal `../`.

2. **High — Authenticated writes and media deletion escape their assigned storage roots. Reproduced.** [projects.ts:68](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/projects.ts:68), [posts.ts:73](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/posts.ts:73), [media.ts:101](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/media.ts:101), [media.ts:134](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/media.ts:134).

An encoded traversal in the media delete route deleted a disposable `.txt` sentinel outside the media directory. All three required the test admin token. The delete endpoint does not constrain the filename to a media extension either.

3. **High — Parallel updates lose successful edits and read partially written JSON. Reproduced.** [files.ts:16](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/lib/files.ts:16), [projects.ts:93](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/projects.ts:93), [regenerate.ts:13](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/lib/regenerate.ts:13).

   Eight simultaneous updates to different fields on one fixture produced six HTTP 200 responses and two HTTP 500 responses. Only five of the eight fields survived, including the loss of a field whose update had returned success. Logs showed JSON parse failures from partial/interleaved writes. `writeFile()` writes directly to the live filename, while requests independently read, merge, write, and regenerate. Readers can encounter truncated files; concurrent writers overwrite each other's changes.

   Keep file storage if desired, but serialize mutations, write temporary files and atomically rename them, and prevent overlapping regeneration. Any lock must cover all Passenger processes that can write the same files; an in-memory mutex only protects one process. Add revision/ETag preconditions to detect stale edits. Atomic replacement alone does not solve lost read-modify-write updates.

4. **High — One damaged record blocks unrelated publishing, and a failed response can still mean the edit was saved. Reproduced.** [regenerate.ts:13](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/lib/regenerate.ts:13), [regenerate.ts:44](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/lib/regenerate.ts:44), [projects.ts:95](/Users/jman/Developer/Web Development/portfolio-attempt-20/backend/src/routes/projects.ts:95).

   Regeneration loads every record using `Promise.all`; one invalid JSON file rejects the whole operation. After inserting one corrupt fixture, updating another project returned 500, yet a subsequent GET showed the new title had persisted. Source content, index, and nav are separate writes without a commit/recovery protocol. A user retrying a failed creation can then get a conflict, or see old list data alongside new detail data.

   Validate stored records, publish projections through a controlled commit process, and provide an integrity/repair command that identifies the exact bad file. Design recovery explicitly: preserve the last valid public projections, report partial failures accurately, and never silently discard damaged content during regeneration.
